# KEY_CONTRIBUTIONS — 핵심 기여

문서 상태: 초안 · 2026-10-28 · WP-7C.

**기재 원칙.** 이 문서는 두 핵심 기여를 *외부에서 관찰할 수 있는 동작*(입력, 출력, 상태 전이, 응답에 나타나는 필드와 코드)으로만 설명한다. 구조 게이트의 판단식, 수리(repair) 규칙과 대체 선택지, 탐색 prior·연산자·부모 선택·승급·예산 추정 규칙, 그 임계값과 데이터 표, 소스 코드는 비공개 core(`SS6`)에만 있으며 이 문서에 적지 않는다. 동작 설명 가운데 "공개 응답에 나타나지 않는다"는 문장은 계약 1.5.0의 공개 응답 투영으로 구현되어 시험을 통과했으며, 배포물·응답·로그 전체를 대상으로 한 누출 검사는 아직 끝나지 않았다(§3).

## 기여 1. 구조 게이트와 수리 (Structure gate + repair)

**해결하는 문제.** 구조 탐색이 제안하거나 사용자가 작성한 검출 모델 구조에는 빌드가 안 되거나, 텐서 형상·채널이 맞지 않거나, 병합·검출 헤드 연결이 잘못된 경우가 섞여 있다. 이런 후보를 GPU 학습까지 보내면 자원이 낭비되고, 실패 원인이 학습 결과와 섞여 해석이 어려워진다.

**외부에서 관찰되는 동작.**

1. **학습 전 CPU 구조 게이트.** 탐색 후보는 학습·평가 작업이 예약되기 전에 core 호스트에서 CPU로 구조 검사를 받는다. 결과는 `PASS`, `FAIL`, `UNVERIFIED` 중 하나다. 구조 런타임을 실행할 수 없는 경우는 `UNVERIFIED`이며 `PASS`로 바뀌지 않는다. `FAIL`·`UNVERIFIED` 후보는 유효 후보 목록과 학습 대상에 들어가지 않는다.
2. **표준 구조 보고서.** 검사 결과는 문서 형식 `mbnas-structure/2`로 기록된다. 보고서에는 10개 검사 항목(`yaml_rows`, `references`, `class_count`, `scales`, `module_support`, `cpu_build`, `reference_forward`, `channels_spatial_stride`, `merge_conditions`, `head_connection`)의 결과와 각 항목의 근거 수준(`declared`, `built`, `forward`, `derived_from_forward`), 진단 코드와 위치가 들어간다. 항목 이름과 근거 수준은 공개 계약 상수이고, 각 항목을 판정하는 규칙은 비공개다.
3. **세 단계 판정의 분리.** 구조 게이트(빌드 가능성), 실행 준비 검증(프로토콜·경로·데이터 split·재개 조건), 평가 후 승급 게이트(rung별 판정)를 서로 다른 단계와 다른 오류 코드로 보고한다. 사용자는 실패가 어느 단계에서 났는지 응답만으로 구분할 수 있다.
4. **제안 단계의 자동 수리.** 탐색 연산(교차·변이 등)이 규칙을 어기는 구조를 만들면 core가 내부에서 수리한 뒤 구조 게이트를 다시 적용한다. 사용자가 받는 생성 후보는 게이트를 통과한 구조이며, 공개 응답에는 블록별 출처(부모 A/B에서 왔는지, 변이되었는지)만 나타나고 수리 여부·위치·사유·전후 값은 나타나지 않는다. 생성 통계(시도 수, 중복 수, 실패 수)는 공개된다.
5. **사용자 구성 입력의 경계.** 사용자 YAML은 빌드 전에 모듈 허용목록과 인자 한도로 먼저 검사되어 허용되지 않은 모듈(`BLOCK_UNSUPPORTED`)이나 범위를 넘는 인자(`ARG_SCHEMA_INVALID`)가 거부된다. 실제 빌드를 포함하는 검사는 자원 제한·시간 제한이 걸린 별도 프로세스에서 실행되며, 한도를 넘으면 정해진 코드로 실패한다.
6. **구조 정체성 기록.** 구성 YAML의 정규 hash(`yaml_hash`), 빌드 구조 hash(`architecture_hash`), 서명 hash(`signature_hash`)를 함께 기록하고, 학습기가 실제로 빌드한 구조의 hash가 후보의 hash와 다르면 `ARCHITECTURE_HASH_MISMATCH`로 그 평가를 무효 처리한다. 구조 검사 이력(최근 5건)이 후보에 남는다.

**비공개로 남는 것.** 형상·병합·헤드 연결 판단식, 수리 규칙·대체 선택지·슬롯 정의, 토큰·깊이·폭 예산 선택지, 수리 이력의 원본(core DB의 감사 기록).

## 기여 2. 탐색 정책과 상태 관리 (Search policy + state)

**해결하는 문제.** 장시간 NAS 실험은 (a) 같은 예산에서 탐색 방식끼리 공정하게 비교되어야 하고, (b) 중단·장애 후에도 같은 결과를 재현해야 하며, (c) 학습을 다른 호스트(고객 GPU)에서 실행해도 결과 기록이 하나의 권위 상태로 일관되어야 한다.

**외부에서 관찰되는 동작.**

1. **탐색 방식(arm)의 구분.** 성능 평가를 하는 탐색(GA, IndependentRandom)과 평가 없이 구조만 생성하는 실행(RandomGeneration)이 별도 실행 경로로 기록된다. 평가 없는 실행의 후보는 적합도·승급이 없고 `NOT_EVALUATED`로 표시되며, 성능 순위나 Pareto front로 표시되지 않는다.
2. **재현 가능한 난수 흐름.** seed·arm·세대마다 독립된 난수 흐름을 쓰고, 0세대는 모든 arm이 같은 고정 prior 공간에서 시작한다. 학습 seed는 탐색 seed와 독립적으로 정해진다. 후보 생성은 journal로 기록되어 재시도·연결 끊김·프로세스 장애 뒤에도 다시 샘플링하지 않고 같은 후보와 안정적인 후보 id를 유지한다. seed 값은 사용자가 입력하고 응답에 표시되는 공개 값이며, 정책의 비공개성은 seed를 숨기는 데 의존하지 않는다.
3. **예산과 승급.** 예산은 arm 단위의 과금 GPU 시간으로 관리되며, 작업 승인(admission) 결정 코드와 상한·청구량·잔여량이 공개된다. rung별 승급 결정 코드와 적합도 값이 공개되며, 적합도 가중치는 사용자 입력 그대로 쓰고 합계가 맞지 않으면 조용히 정규화하지 않고 거부한다. 적합도와 승급 판정은 core만 계산하고 runner는 측정값만 보고한다.
4. **단일 권위 상태와 원격 실행의 일관성.** run·후보·평가·작업·비용·checkpoint의 권위 상태는 core 한 곳에 있다. 원격 runner는 작업을 임대(lease)받아 주기적으로 연장하고, 모든 쓰기 요청은 작업·runner·시도 번호로 검사(fencing)되며 작업별 서명 ticket을 요구한다. 결과 commit은 멱등이다(같은 본문 재전송은 같은 응답, 다른 본문은 `RESULT_CONFLICT`). runner가 사라지면 core가 만료된 lease를 회수하고, 다음 시도는 가장 최근의 full-state checkpoint에서 이어 가며 손실 시간은 별도로 기록된다.
5. **일시정지와 재개.** 일시정지 요청은 즉시 완료로 표시되지 않는다. 학습이 안전 경계에 도달해 full-state checkpoint(모델, EMA, optimizer, scheduler, AMP, RNG, sampler 상태)를 저장한 뒤 `PAUSED`가 된다. 재개 전에는 프로토콜·데이터·구조·recipe·checksum을 검사하며, 상태가 없거나 손상되었으면 가중치만으로 대체하지 않고 구체적인 코드로 차단한다.
6. **정책 상태의 비노출.** runner에 전달되는 작업 봉투(JobEnvelope)와 공개 응답에는 사용자 프로토콜·작업 명세·후보의 공개 행만 들어가고, 탐색 prior·부모 풀·탐색 내부 상태·예산 추정 내부값은 들어가지 않는다.

**비공개로 남는 것.** prior 표와 draw 구조, 난수 흐름 키 유도식, GA 연산자 구현과 부모 선택 기록, 승급·예산 추정·종료 규칙과 그 임계값.
