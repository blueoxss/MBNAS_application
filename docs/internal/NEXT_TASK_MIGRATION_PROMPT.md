- 원본의 `.git`, branches, tags, reflog, hooks, remote 설정, Git 이력을 대상으로 복사하지 않는다. fork·mirror·`push --mirror`·이력 import를 사용하지 않는다. 새 대상은 정리 결과의 독립 초기 이력으로 시작하되 출처·저작권·라이선스와 원본 기준 commit은 문서로 보존한다.
- `.env`, 토큰, 키, 인증서의 개인키, 운영 DB, 실제 로그·개인정보, 내부 자격증명은 이관하지 않는다. 필요한 설정은 안전한 예제와 변수명으로 제공한다. 보고서·diff에도 비밀 값을 재출력하지 않는다.
- 새 저장소를 만들기 전에 `blueoxss` 계정/조직 아래 생성 권한과 사용자 승인을 확인한다. 권한 부족이면 산출물과 정확한 다음 조치만 제공하고 원격 작업은 보류한다.

## 4. 공개 경계와 핵심 기여 대응
실제 mbnas_core, mbnas_server, mbnas_runner, mbnas_model_runtime, mbnas_contracts, mbnas_web를 찾아 각 실행 주체와 의존 방향을 기록한다. owner 전체본에는 코어가 있고 public은 원격 코어를 호출한다는 구조를 실제 코드로 확인한다. 공개본에 core 정책·내부 상태·비밀을 넣지 않는다.

## 5. 제외 정책과 staging
원본 저장소는 읽기 전용으로 유지한다. 원본에 정리용 브랜치를 만들거나 직접 수정하지 말고, 별도 WORK_ROOT의 사본에서만 필요한 편집을 한다. 패키지는 owner/public/registration별 allowlist staging으로 구성하며, staging 밖 원본을 삭제하지 않는다. 정리 결과의 대상 반영은 13절의 검증·보고·승인 절차를 따른다. 원본 push, 공개 release, 실제 기관 제출은 수행하지 않는다.
일반 제외 후보: .git, 불필요한 .github 협업 설정, 실행 참조 없는 .gitignore/.ignore/.rgignore, AGENTS.md·CLAUDE.md 등 에이전트 지침과 대화, IDE 설정, OS 잡파일, 캐시·가상환경·node_modules, 시험 보고서·coverage, 실제 로그·PID·운영 DB, 백업·임시 파일, 실제 데이터셋·가중치·학습 결과와 자격증명.
일괄 삭제 금지: .dockerignore·.npmignore·.gitattributes·.gitmodules, manifest·lock·requirements·constraints, 설치·검증 스크립트, 호출되는 tests/fixture, operator·스키마·migration·모델 설정·웹 dist, LICENSE·NOTICE·THIRD_PARTY_NOTICES. 각각의 사용·설치·법적 고지 책임을 확인하고 결정한다. 원본 데이터와 작은 공개 smoke 자원을 구분한다. 제외 이유와 유지 예외를 실제 경로별로 기록한다.

## 7. 주석·설명 문체 정리
"요청에 따라", "이제 완료했습니다", "아래 코드", 가상 작업자·라운드 설명, 장황한 자기 평가·홍보 문구, 코드를 그대로 읽어 주는 주석과 오래된 임시 안내를 위치별로 찾는다. 문체만으로 AI 생성 여부를 확정하지 말고 개선 후보로 분류한다. 실제 책임·입출력·제약·예외를 짧고 검증 가능한 문장으로 바꾼다.
유지할 주석은 알고리즘 선택 이유, 단위·불변조건, 호환성 근거, 보안 경계, 알려진 제약, 외부 출처다. TODO/FIXME가 실제 결함을 가리키면 결함을 해결하거나 그대로 추적하며 문구만 지워 완료로 만들지 않는다. 주석·docstring 수정표에 파일·행·기존 문제 유형·변경 요지·영향 검증을 기록한다. 단순 정규식으로 모든 주석을 제거하지 않는다.

## 8. 코드 정리의 동작 보존
죽은 코드·중복·미사용 import·임시 디버그 출력을 정리하되 호출 관계·동적 import·등록 키·부수 효과를 확인한다. 공개 API·CLI·설정 키·기본값·오류 코드·DB·checkpoint 구조와 NAS seed/RNG·평가 가중치·승급·예산·종료 의미를 임의 변경하지 않는다.
평가 OFF는 무작위 후보 생성→구조 검사→유효 후보 저장이며 학습·성능 평가·fitness·승급을 수행하지 않는다. 미평가 지표는 null로 유지한다. 구조 PASS와 학습·성능 성공을 구분한다. pause/resume/cancel과 전체 상태 복구 의미를 보존한다.
shebang·인코딩·type ignore·noqa·coverage pragma·doctest·런타임에서 읽는 docstring/주석은 기능 영향이 있으므로 확인한다. *_pb2.py·생성 타입/클라이언트는 원본 스키마와 생성기로 재생성하고, 생성 경고만 삭제하지 않는다. 주석만 바꾼 변경과 동작 변경을 분리해 적합한 lint·typecheck·unit·integration·smoke를 수행한다. 대규모 GPU 탐색·학습은 시작하지 말고 필요한 최소 검증을 격리 환경에서 수행한다.

## 9. 프로그램 목록과 통계 산출
정리·검증 후 확정된 registration 소스 집합에서 첨부 "002 프로그램 목록 - 프로파일.xls"의 7개 열(순번/파일명/기능/라인수/언어/창작자/창작연월일)을 채운다. 원본 양식을 실제로 확보했는지 먼저 확인한다. 양식이 없으면 동일 7개 열의 검토용 CSV/XLSX와 실제 집계를 먼저 만들고, 원본 양식 적용·최종 XLS 확정만 미완료로 표시한다. 다른 사례의 프로그램명·개인·날짜·행수는 복사하지 않는다. 상대 전체 경로로 파일을 식별하고 실제 함수·호출 책임을 읽어 입력→처리→출력을 짧게 기술한다. docstring만 복사하거나 모든 파일에 같은 설명을 붙이지 않는다.
파일별 원문 byte·SHA-256·언어·인코딩·개행을 기록하고 물리행은 엄격히 디코딩한 원문에 splitlines()를 적용해 주석·빈 줄을 포함한다. 판독 실패·바이너리를 0줄로 바꾸지 말고 별도 분류한다. 바이너리는 원문 소스 합계에 섞지 않는다. 외부·생성·자체 수정분의 합계를 구분하고, manifest·문서·목록 자체 포함 여부를 명시해 자기참조 집계를 피한다.
file_count, physical_lines, source_bytes, archive_bytes를 별도로 산출한다. 참고 사례의 규모는 ZIP byte였으나 최종 규모 입력 기준은 기관 요구로 확인한다. 소스가 없으면 미산출로 둔다. Git 작성자·commit 날짜·파일 수정 시각을 창작자·창작완료일로 자동 대입하지 않는다. 신원·완료일은 담당자 확인값을 사용하고 모르면 명시한다.

## 10. XLS 원본 양식과 실제 형식
원본은 사본으로 읽고 제목·열 순서·너비·정렬·인쇄 범위를 최대한 보존한다. 실제 데이터 마지막 행까지 SUM을 적용한다. 마지막 두 행의 714+237줄을 합계에서 누락한 기존 사례와 같은 수식 오류를 회귀 검증하되, 예제 숫자를 실제 MBNAS 목록에 넣지 않는다.
합계는 수식으로 두고 독립 집계와 비교한다. 실제 파일 집합이 없으면 빈 SUM의 0을 완료값으로 표시하지 않는다. 숫자는 숫자, 확인된 날짜는 날짜 형식으로 저장하고 모든 시트를 렌더링해 파일명·기능·숫자 잘림을 확인한다. .xls가 요구되면 실제 BIFF XLS로 내보내고 다시 열어 값·수식·병합·합계를 확인한다. XLSX 확장자만 .xls로 바꾸지 않는다. 도구상 불가능하면 실제 생성 형식과 제한을 명시한다.

## 11. 패키징·독립성·Windows 압축
프로필별 allowlist manifest와 실제 staging·최종 압축 해제본의 누락/추가/중복 파일을 비교한다. 상대 경로 탈출·심볼릭 링크·대소문자 충돌·Windows 예약 이름·과도한 경로 길이·Git LFS 포인터를 검사한다. 원본 checkout·기존 PYTHONPATH·editable 경로·symlink 없이 설치와 실행을 확인한다.
owner 전체 실행과 public의 실제 원격 core 연결 실행을 별도로 검증한다. 공개본에 core 구현이 없으면 완전 오프라인 NAS라고 쓰지 않는다. 키·토큰·개인정보·내부 절대경로를 검사하고 민감한 값을 보고서에 재출력하지 않는다. 실행 확인은 프로그램 관련 자원·의존 패키지·허용 입력으로 이루어져야 한다.
사용자 제공 업로드 조건은 Windows에서 ZIP 생성, 파일당 190MB 이하, 초과 시 분할이다. Windows에서 최종 ZIP을 생성하고 압축 해제·파일 집합·파일별 hash·ZIP byte를 다시 검증한다. Linux에서 만든 ZIP을 Windows 생성본이라고 표시하지 않는다. Windows 실행이 불가능하면 staging·목록까지 완성하고 Windows 압축만 미완료로 구분한다. 크기 초과 시 접수 화면이 수용하는 분할 형식을 확인한다. 독립 ZIP 여러 개를 요구하면 파일 단위로 나누고 중복을 제거한다. 표준 분할압축을 허용하면 그 형식으로 생성한 뒤 전체 볼륨을 함께 복원해 원래 파일 집합·hash와 대조한다. 임의로 소스 내용을 절단하지 않는다. 각 ZIP/볼륨 크기·합계·전체 소스 합계를 구분하고 manifest에 기록한다.

## 12. 누적 검토와 최종 인계
iterative-feedback-evaluator 스킬이 있으면 실제 지침을 읽어 적용한다. C01~C12는 서로 다른 관점으로 각각 네 기준을 25점씩 평가한다. 관점은 C01 접근/버전/원본·대상 식별, C02 요구/프로필·이관 범위, C03 의존성, C04 공개 경계, C05 제외 정책, C06 출처/권리, C07 주석 문체, C08 동작 보존, C09 목록/통계, C10 XLS 서식, C11 패키징/Windows, C12 재현/이관/원본 보존·인계다. 각 관점의 네 기준을 먼저 구체화하고 근거가 없는 점수를 부여하지 않는다.
각 기준셋에서 평가→구체 피드백→점검→수정→재검증을 수행한다. threshold=90, 점수 90점 초과, 미해결 Blocker/Critical 0, 해당 필수 검증 통과를 모두 만족해야 다음 정식 기준셋으로 이동한다. 이전 최종본이 다음 입력이다. 기준셋별 네 항목 점수·근거 위치·입출력 hash·실제 변경·검증 명령/결과·잔여 조건을 남긴다. 최대 다섯 수정 회차 후에도 외부 자료가 필요하면 중단 사유와 최소 다음 행동을 기록한다.
접근 자료가 없어 정식 누적 통과가 막히면 독립적으로 가능한 문안·서식·분류 지침은 계속 완성한다. 이후 관점의 독립 진단을 12개 누적 통과로 꾸미지 않는다. 문서 품질, 실제 코드 변경 검증, 설치·배포·권리 검토·접수 상태를 분리한다.
검토는 산출물의 마지막 변경을 반영한다. 검토 후 파일이 바뀌면 영향받는 기준셋·검증·목록·hash를 다시 갱신한다. C12의 원격 이관 후 검증은 실제 push 뒤에만 통과시킬 수 있다. 승인 대기 단계의 로컬 검증을 원격 이관 완료나 C01~C12 전체 통과로 표시하지 않는다. 목록·문안은 최종 압축 해제 집합과 다시 대조한다. 등록 수리·원본 전체 창작·완전 보안을 확약하지 않는다.

## 13. 검증된 결과를 별도 저장소에 반영

### A. 로컬 이관 후보 확정
1. 실제 소스 분석·정리·프로필별 staging을 끝내고, 대상에 넣을 확정된 등록·배포 범위를 `MIGRATION_PLAN.md`에 적는다. 대상은 단일 프로필 또는 명시적인 경로 구획으로 구성하되 owner/public/registration의 경계와 사용법을 유지한다. 코어 포함·공개 범위가 미확정이면 해당 파일은 후보 보류로 두고 자동 복사하지 않는다. 핵심 기여 구현이 제출 범위에 없으면 그 사실을 숨기지 않는다.
2. `TARGET_ALLOWLIST.csv`에 `source_path`, `work_path`, `target_path`, `profile`, `action`, `origin`, `source_sha256`, `target_sha256`, `reason`, `verification`을 기록한다. 원본 대비 그대로 복사, 수정 사본, 신규 문서를 구분한다. 승인 범위 밖의 파일이나 미확인 경로를 넣지 않는다.
3. `TARGET_WORK_ROOT`에는 allowlist 파일만 복사한다. 파일 내용·상대 경로·실행 권한·필요 자원을 보존하고, 원본을 가리키는 symlink·editable 의존성·절대 경로는 없앤 뒤 독립성을 검증한다. 원본의 Git 이력은 가져오지 않고, 대상 작업 공간에서만 독립 Git 저장소를 초기화한다. 대상의 새 `.git`은 운영 메타데이터이며 패키지·등록 소스 목록에는 포함하지 않는다.
4. 로컬 대상 사본에서 설치·lint·typecheck·unit·integration·smoke 중 실제 프로젝트에 적용되는 검증을 다시 수행한다. 명령, 환경·버전, 시각, 종료 코드, 결과와 실패/미실행 사유를 남긴다. 존재하지 않는 테스트를 통과했다고 하지 않는다. 외부 core·GPU·Windows가 없어 불가능한 항목은 `BLOCKED` 또는 `NOT_RUN`으로 분리한다. 생략이 소스 이관을 막는지, ZIP/기관 제출만 막는지 명시한다.
5. 원본 기준선과 마지막 상태를 비교해 원본 HEAD·브랜치·기존 dirty/untracked 상태와 파일 hash의 불변을 확인한다. 변경이 발견되면 원인을 보고하고 임의로 원상복구하거나 사용자의 작업을 덮어쓰지 않는다.
6. `README.md`에는 등록명/표시명/영문명, 실제 포함 범위, 설치·실행·검증법, 원본 출처, 정리 기준 commit, 빠진 자원·외부 core 필요 여부를 정확히 적는다. 버전 `1.0`은 사용자가 의도한 저장소명과 프로그램의 실제 버전이 일치하는지 확인한 뒤 확정한다. 문서·manifest·목록의 버전을 임의로 다르게 쓰지 않는다.

### B. 생성·push 전 보고와 승인
원격 변경 전에 다음을 한 번에 보고하고, **정확한 저장소명과 포함 범위에 대한 사용자 승인을 기다린다**. 질문 대기 중에도 의존하지 않는 로컬 산출물·검증은 계속 완성한다.

- 원본 URL과 실제 기준 branch/commit 또는 승인된 로컬 스냅샷 식별자
- 의도 대상 `https://github.com/blueoxss/MBNAS_application_ver1.0` 및 입력 링크 `.../MBNAS_application_ver1`과의 차이, 조회 결과와 최종 사용할 전체 URL
- 신규 생성 여부, 기본 `PRIVATE`, 생성·push 권한 확인 결과
- 포함 프로필·디렉터리, 파일 수·실제 용량·주요 제외 항목, 코어 포함 여부
- 원본 대비 변경 요약, 라이선스/출처 보존, 시크릿 검사와 독립 실행 검증 결과
- 미완료 검증·담당자/기관 확인값·Windows ZIP 상태, 이관에 영향을 주는 blocker
- 수행할 원격 작업: 확정된 이름의 신규 private 저장소 생성과 최초 push. 대상이 이미 있다면 이를 보존하고 별도 신규 이름을 확정한 뒤 다시 승인받을 것

승인이 없으면 `READY_FOR_APPROVAL` 또는 해당 `BLOCKED_*`로 끝내고 실제 산출물 경로와 다음 행동을 제공한다. 파일을 준비한 사실과 저장소에 반영한 사실을 구분한다. 원격 작업의 승인 대기는 정리 산출물을 제공하지 않을 이유가 아니다.

### C. 승인된 원격 반영
1. 승인을 받은 뒤, 원격 변경 직전에 대상명·소유자·존재 여부·권한을 다시 읽어 확인한다. 승인 이후 대상이 생겼거나 내용이 바뀌면 생성·push를 중지하고 달라진 상태를 보고한다.
2. 대상이 없고 신규 생성 승인이 있으면 정확한 이름으로 private 저장소를 생성한다. 자동 README/라이선스 초기화로 다른 초기 이력이 생기지 않도록 하고, 검증된 대상 작업 공간의 파일만 최초 commit으로 반영한다. 비밀·원본 `.git`·미승인 파일이 index에 없는지 commit 전 확인한다.
3. 대상 remote URL과 소유자가 승인된 TARGET_REPO와 일치하고 SOURCE_REPO가 아님을 확인한 뒤 정상 push한다. 강제 push, mirror push, 원본 push는 금지한다. 기존 대상 저장소는 변경하지 않는다.
4. 전송 실패 시 실제 원격 상태와 생성/commit/push 성공 범위를 먼저 확인한다. 성공한 작업을 중복 수행하거나 실패를 피하려고 강제 push하지 않는다. 권한·네트워크 문제를 해결 가능한 범위에서 처리하고, 추가 권한이 필요하면 정확한 대상·행동·이유만 보고한다.

### D. 원격 반영 후 검증
1. GitHub에서 실제 저장소명·소유자·private 상태·기준 branch와 최종 commit SHA를 확인한다. 로컬 commit과 원격 commit의 일치를 확인한다.
2. 대상 저장소를 새 임시 경로에 다시 받아 실제 tracked 파일 집합을 `TARGET_ALLOWLIST.csv`와 대조한다. 원본 Git 이력·시크릿·불필요 파일이 섞이지 않았는지 검사한다. 다운로드 방식에 따라 생기는 새 `.git` 자체는 소스 집합에서 제외한다.
3. 전송 대상 파일의 byte hash를 기준 manifest와 비교한다. 줄바꿈 정규화가 있으면 정책을 기록하고 정규화된 최종 bytes로 목록·통계를 갱신해 다시 검증한다. 설명 없이 hash 불일치를 무시하지 않는다.
4. 새 checkout만으로 가능한 최소 설치·실행 smoke를 재수행하고, 대상 README의 명령과 프로필 경계가 맞는지 확인한다. 원본 checkout이나 기존 경로를 참조해 우연히 통과하지 않게 한다.
5. 원본의 파일·HEAD·작업 상태가 그대로인지 마지막으로 확인한다. `MIGRATION_REPORT.md`에 실제 URL·branch·commit·파일 수·hash 비교·원본 보존·잔여 제한을 남긴다. push만 성공하고 검증이 남았으면 `PUSHED_PENDING_VERIFICATION`이며 `MIGRATED_VERIFIED`로 쓰지 않는다.

## 14. 최종 산출물·완료 판정·응답 형식

가능한 산출물부터 제공하고, 없는 자료는 가짜 행이나 0으로 채우지 않는다. 다음 파일명을 일관되게 사용한다.

- `FILE_INVENTORY.csv`: 실제 원본 파일 전수 분류
- `EXCLUSION_CANDIDATES.csv`, `EXCLUSION_RULES.csv`: 실제 제외 후보와 일반 정책 분리
- `PROFILE_ALLOWLISTS/`: owner/public/registration의 확정 포함 집합
- `REGISTRATION_SOURCE_FILES.csv`: 등록 소스의 최종 파일 집합
- `COMMENT_AND_CODE_CHANGES.md`: 주석·코드 변경과 영향 검증
- `LICENSE_AND_PROVENANCE.md`: 자체/외부/수정/생성 구분과 출처·라이선스
- `VERIFY_RESULTS.json`: 실제 실행한 검증 결과와 `PASS`/`FAIL`/`BLOCKED`/`NOT_RUN`/`NOT_APPLICABLE` 근거
- `프로그램목록_프로파일_MBNAS.xls`: 실제 BIFF XLS 원본 양식 적용본. 불가능하면 생성한 CSV/XLSX와 제한을 별도 표기
- `METRICS.json`, `SOURCE_MANIFEST.json`: 프로필별 파일 수·물리행·소스 byte·archive byte, 기준 스냅샷과 최종 hash
- `TARGET_ALLOWLIST.csv`, `MIGRATION_PLAN.md`, `MIGRATION_REPORT.md`: 이관 범위·승인 상태·실제 반영과 원본 보존 검증
- `REVIEW_LOG.md`: C01~C12 점수·근거·수정 회차·재검증·남은 조건
- 필요한 프로필별 ZIP, `SHA256SUMS.txt`: 실제 생성 환경·크기·분할 형태·복원 검증 포함

보고서·목록·ZIP을 대상 Git에 무조건 넣지 말고, 이관 allowlist에 승인된 것만 반영한다. 상세 내부 검토 기록·민감한 경로 정보·대용량 ZIP은 로컬 인계물로 분리할 수 있다. 인계 문서 생성에 따른 자기참조 hash/통계를 피하도록 소스 집합과 검토·포장 산출물 집합을 명시적으로 나눈다.

최종 응답은 다음 순서로 간결하게 작성한다.

1. **완료 상태:** 로컬 정리, 목록/XLS, 검증, Windows ZIP, 대상 생성·push, 원격 재검증을 각각 실제 상태로 표시한다.
2. **바로 사용할 산출물:** 파일·폴더·다운로드 위치를 먼저 제공한다.
3. **원본과 대상:** 원본 기준 commit/스냅샷, 확인된 대상 URL·private 여부, 실제 원격 commit 또는 아직 반영하지 않은 사유.
4. **핵심 결과:** 프로필별 파일 수·물리행·소스/ZIP byte, 제외·수정·출처 보존 요약. 미산출은 미산출로 표시한다.
5. **검증과 검토:** 실행한 검증, C01~C12의 실제 통과 범위, 원본 불변·allowlist/hash 대조 결과.
6. **남은 확인:** 저장소명/권한/승인/코어 범위/기관 양식/창작자·완료일 등 실제로 필요한 최소 다음 행동.

완료 표현을 구분하라. `LOCAL_PREPARED`는 로컬 정리 산출물이 준비된 상태, `READY_FOR_APPROVAL`은 원격 변경 승인 대기, `PUSHED_PENDING_VERIFICATION`은 push 후 검증 미완료, `MIGRATED_VERIFIED`는 승인된 별도 저장소의 파일·commit·독립성 검증까지 완료된 상태다. 원격 이관이 끝나도 기관 제출·등록 수리·전체 권리 검토가 완료되었다고 주장하지 않는다. 소스 접근 불가·범위 미확정·권한 부족은 각각 정확한 blocker와 이미 완료한 작업을 함께 보고한다.
